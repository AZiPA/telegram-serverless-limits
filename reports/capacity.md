# Telegram Serverless: CPU, memory, SQLite and concurrency

Measured on **October 9, 2026**, using one early-access bot and `@tgcloud/cli` 0.2.0. The [snapshot](2026-10-09/) contains 394 recorded invocations, including [84 later buffer probes](buffer-limit.md). Bot identifiers are redacted; measurements are unchanged.

Probes ran through the management API's `/manage/run` endpoint on Telegram infrastructure. No modules were deployed. These observations do not establish production bot throughput or official resource quotas.

## Memory

Arrays of non-integer JavaScript numbers passed at **127 MiB of element payload (4/4 runs)** and failed at **128 MiB (4/4)** with `Terminated: Memory limit exceeded`. Payload is estimated at eight bytes per element. Array objects, runtime overhead and other heap allocations are excluded, so this is a workload boundary near 128 MiB, not a readout of V8's configured limit.

Separately, 1,024 `Uint8Array` buffers of 1 MiB were allocated, filled and checked while held together: **1 GiB total**. The initial buffer test stopped at its own 1 GiB ceiling. Later tests fully wrote **6 GiB** and sometimes allocated **8 GiB**; see the [buffer report](buffer-limit.md) for the inconsistent boundary.

## CPU execution time

Four uninterrupted `xorshift32` workloads stopped after **3,002.8–3,016.5 ms** with `Terminated: CPU timer exceeded`. One billion iterations completed in a median **1,366.1 ms** across four successful runs.

Timing uses the server's `time` field, converted to milliseconds. `Date.now()` did not advance inside synchronous loops, and `performance.now()` was unavailable. This test measures continuous computation; it does not determine the maximum duration of a handler waiting on HTTP or database work.

## SQLite storage

A separate table used `INTEGER PRIMARY KEY` and a BLOB column, with **64 KiB per row** generated by `randomblob()`. Counting rows and summing `length(payload)` confirmed **496 MiB = 520,093,696 bytes** of stored payload.

An additional 8 MiB was rejected; a subsequent read still showed 496 MiB. Adding 1 MiB also failed. Observed errors:

```text
Sqlite database size limit exceeded
Sqlite query failed (commit) [13] database or disk is full
```

Row layout and indexes consume space too. This does not prove an exact 500 or 512 MiB quota, or reveal the physical disk size.

## Concurrent calls

Each call ran 250 million iterations. Batch time uses the local monotonic clock and includes network latency. No automatic retries were used in this test.

| Simultaneous calls | Successful batches | Median batch time | Relative throughput |
| ---: | ---: | ---: | ---: |
| 1 | 3/3 | 398.8 ms | 1.00× |
| 2 | 3/3 | 398.0 ms | 2.00× |
| 4 | 3/3 | 399.3 ms | 4.00× |
| 8 | 3/3 | 401.0 ms | 7.96× |
| 16 | 0/1 | Not comparable | 11 calls rate-limited |

In the 16-call batch, five calls succeeded and eleven returned HTTP 429, `RATE_LIMITED`, with `retry_after: 7`. This exposes a management API rate limit, not a physical core count or a production concurrency limit. The API's exact request quota was not determined.

One single-call timing was an unexplained outlier at 2,560.9 ms of server time, versus roughly 344 ms normally. The medians are not latency guarantees. [Batch records](2026-10-09/parallel.json) retain all results.

## Cleanup and runtime restrictions

All test tables were removed. A final write/read check stored 1 KiB, read it, dropped its table, and confirmed an empty table list. A later `SELECT 1` also passed. See [summary.json](2026-10-09/summary.json) and [buffer-summary.json](2026-10-09/buffer-summary.json).

`PRAGMA page_size`, `page_count` and `freelist_count` were denied. `SAVEPOINT` was denied, `dbstat` was absent, and `VACUUM` was unsupported. Logical cleanup and database usability were verified; physical page reclamation could not be measured. Host CPU model, core count, RAM and disk capacity were unavailable.

## Reproduce

After the [initial setup](../README.md#try-a-small-diagnostic), run stages separately:

```bash
npm run probe -- memory
npm run probe -- cpu
npm run probe -- confirm
npm run probe -- parallel
npm run probe -- storage
```

`memory` searches the JS-array boundary and tests buffers up to 1 GiB. `confirm` repeats the observed heap and CPU cases. `parallel` stops on a failed call, including HTTP 429.

**Run `storage` only on a disposable test bot, one storage test at a time.** It fills the available quota in a randomly named `__tg_probe_…` table, then drops its own table and verifies cleanup. If interrupted, run:

```bash
npm run probe -- cleanup
```

Cleanup uses the ignored `reports/storage-state.json`, checks the linked bot, and addresses only the recorded test table. Keep that file until cleanup succeeds. Individual probes and cleanup honor `retry_after` with at most three retries; ambiguous network write failures are not automatically retried.

Live output is appended to `reports/probes.jsonl`. The [published log](2026-10-09/probes.jsonl) is a separate snapshot. Early entries predate source-hash recording; the code evolved during the investigation. `experiments/` is outside the deployable `tgcloud/` directory.
